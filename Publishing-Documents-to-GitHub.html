Publishing Documents to GitHub

A general walkthrough for putting a public-facing HTML page online, free, using GitHub Pages

Share this guide at bit.ly/GitHubwalkthrough

This is the same method behind ARIC's own public resource pages (staff directories, schedules, help guides). It costs nothing, takes about fifteen minutes to set up the first time, and after that, publishing a new or updated document is just a file upload.

Start with a formatting example

Before building your own page, look at one of the two format examples below. Each is a real, working layout filled with placeholder (lorem ipsum) text — not a real document.

The fastest way to build your own: feed your AI assistant (Copilot, Gemini, Claude, whatever your institution provides) the example page's HTML, your logo file, and your actual content, and ask it to match the example's layout and color scheme using your logo and text instead. You'll spend far less time fighting with formatting by hand.

Step 1 — Create a GitHub account

Sign up at github.com

Go to github.com/signup and create a free account with an email address, a password, and a username.

Name it generically, not personally. Skip a username tied to one person (e.g. jsmith-ric5). RIC directors and coordinators change roles, and whoever owns this account controls every page published under it. Use something tied to the program or center instead — e.g. region5ric, [center]resources, or a shared department name — so the account and its password can be documented and handed off cleanly to a successor or a colleague, the same way you'd hand off a shared inbox.
Check your university's branding rules before you publish anything. A GitHub Pages site is a public website. If it will carry your university's name, seal, wordmark, or official colors, run it past your institution's communications or brand office first, the same as you would for any other public-facing site. This is especially worth doing before your first upload — it's much easier to check up front than to redo it later.

Verify your email

GitHub will send a confirmation code or link — verify it before continuing. Store the account's login (username, password, and recovery email) somewhere your team already keeps shared credentials, not just in one person's head or personal inbox.

Step 2 — Create a repository

Click "New" to start a repository

A repository ("repo") is just a folder that lives on GitHub. Give it a clear, generic name that matches your account's purpose — e.g. region5-resources or 2026 for a year-based document set.

Keep it Public. Free GitHub Pages hosting requires a public repository. Since these are meant to be public resource pages anyway, that's not a concession — that's the point.

Step 3 — Upload your files

Add your HTML files (and any logos or images they reference)

Inside the repository, use Add file → Upload files, then drag your finished HTML page — and any image files it points to, like your logo — into the browser window. Write a short note describing the change, then commit.

Step 4 — Turn on GitHub Pages

Point GitHub at your files

Open the repository's Settings tab, then Pages in the left sidebar. Under "Build and deployment," set Source to "Deploy from a branch," then set the branch to main and the folder to / (root). Save.

You have to upload a file before Pages will activate. If your repository is still empty, this screen will tell you so and won't let you turn Pages on yet — upload at least one file first (Step 3), then come back here.

Before a file is uploaded — Pages is disabled

After a file is uploaded and Pages is turned on

Give it a minute or two after saving. Your page will be reachable at:

https://<your-username>.github.io/<your-repo-name>/<your-file>.html

Step 5 — Share and maintain the link

Shorten it, and know how to update it

  • Run the long GitHub Pages URL through a link shortener (e.g. bit.ly) so it's easy to print, say aloud, or put on a flyer.
  • To update the page later, go back into the repository and upload a new version of the file with the same name — it overwrites the old one and the short link keeps working.
  • Document the account's login and the repository name somewhere your team already keeps shared records, so the next person doesn't have to start over.
